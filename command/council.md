# 多模型议会 · 公开模板（静默模式）

用户的问题：

$ARGUMENTS

---

## 四条铁律

1. **全程静默**。除了最后那一条汇报，聊天框里不出现任何中间叙述：不说“我正在调用”“让我看看”“首先我们需要”。
   工具调用本身会显示，那是系统行为；**你不要额外写字**。
2. **不编造**。没真调用子代理，就不许出现多份方案。
3. **不停机**。任何席位失败、超时、502，都按「降级」处理，继续往下走。
4. **只给结论**。最终回复控制在 500 字内，细节一律落盘。

---

## 模式（由用户参数决定，默认第一档）

| 模式 | 触发 | 席位 | 阶段 | 典型耗时 |
|---|---|---|---|---|
| **默认** | 无参数 | 5 席（架构/工程/反方/视觉/学者） | 提案 + 互评 | 60–90s |
| **quick** | 含 `quick` | 架构师 + 工程师 | 仅提案 | 20–30s |
| **wide** | 含 `wide` | 默认 5 席 + 1 个补充模型 | 提案 + 互评 | 100–130s |
| **show** | 含 `show` | 同默认 | 同默认 | +0 |

`show` 只改变**展示**方式：把各席位原文贴进对话。不加就只给结论表 + 存档路径。

> 模型名不在本文件里写死。每个席位的模型由 `agents/council-*.md` 的 frontmatter 决定；
> 没配就继承当前会话模型。详细配法见 `README.md` 第 5 节。

## 阶段 0 · 备料（自己内部完成，不输出）

1. 代码类问题：先用 `read` / `grep` / `glob` 查事实。
2. 方案类问题：直接梳理。
3. **如果用户指的是“刚才那个方案 / 上一条回答 / 你刚说的”**：
   - 把那份已有方案原文抓出来，记作 **`P0`**，一起放进上下文包（不要改写、不要美化）。
   - 阶段 1 仍出 5 份新提案，但要在 prompt 里明确写：「以下是用户已经看过、认为可行的 `P0`，你的任务**不是重新发明**，而是指出它的问题、补齐它、或者说明它比你的想法更好」。
   - 阶段 2 匿名编号时把 `P0` 也编进去（`A–F` 中的一个），**不做特殊标记**，否则议员会偏袒它。
   - 阶段 3 若 `P0` 得分不低于最高分 -15%，**优先保留 `P0`**，只把其他提案的改进点合并进去。用户已经认可的东西，不轻易推翻。
4. 内部写一份 **上下文包**（≤1200 字）：真实目标 / 成功标准 / 现状事实含报错原文 / 硬约束 / 验证手段。**不要打印出来。**
5. 信息不足且猜不出 → 用 `question` 一次性问完（≤3 个）。
6. 建存档目录：`${COUNCIL_DIR:-.council}/<yyyyMMdd-HHmm>/`。
   - 如果当前目录不可写，退到系统临时目录，并在最终汇报里写明实际路径。
   - 存档目录不要提交到 Git（`.council/` 已忽略）。

## 阶段 1 · 独立提案（并行，立即全发）

**同一条消息里一次发起**，不串行、不等待：

| 席位 | 子代理 | 领域 | 权重 |
|---|---|---|---|
| 架构师 | `council-architect` | 架构、接口、长脚本 | 1.3 |
| 工程师 | `council-coder` | 代码实现、性能、边界 | 1.2 |
| 反方 | `council-critic` | 质疑前提、隐藏风险 | 1.1 |
| 视觉 | `council-vision` | 看图、配色、交叉验证 | 1.0 |
| 学者 | `council-scholar` | 中文、需求理解、长文档 | 0.9 |
| *(wide)* 补充 | `general` + 你配置的补充模型 | 第二视角 | 0.8 |

每个 prompt 必须包含：
- 原问题 + 上下文包（逐字一致）
- 「**不超过 400 字**，不复述题目，不写客套话」
- 固定输出：核心思路 / 具体步骤 / 关键决策 / 风险 / **KILL CRITERIA** / 最有把握与最没把握
- 允许它把完整版写到 `<存档目录>/<席位>.md`（目录已建好，路径写给它）

> `wide` 的补充模型必须是你真实配置过的。没配就跳过，不要假装有第六席。

---

## 阶段 2 · 匿名互评（并行）

1. 把所有候选（5 份新提案，有 `P0` 时加上 `P0`，`wide` 再加补充那份）统一匿名编号 `A/B/C/...`，映射表只你自己知道。
2. 同一批子代理并行再发一次：上下文包 + 全部匿名提案 + 下面模板。
3. 要求「**不超过 300 字**」，并严格以排名结尾：

```
【硬伤】逐份，一句话
【新增洞察】所有提案都漏掉的一点

FINAL RANKING:
1. Response X
2. Response Y
3. Response Z
4. Response W
```

`quick` 模式跳过本阶段。

---

## 阶段 3 · 收敛（自己算，不输出过程）

### 计分
- **加权 Borda**：第 1 名 N 分 … 第 N 名 1 分（N = **候选方案数**，不是席位数），乘评审员权重后累加。
- **加权均值**：各席位 x/10 按权重平均。
- 以加权 Borda 为主，均值只作参考。

### 裁决
- 共识项直接采纳。
- 分歧项按证据裁决：能查文档就查，能被代码事实否定的就否定。
- 被 2 席以上指出的硬伤，无论出自哪份，必须修。
- **不许制造假共识**：出现接近对半的分裂（加权分差 <15%），选**可逆**方案并写下切换条件；影响大就直接问用户（≤3 问）。

### 定稿
```
目标 / 选定路线 + 理由 / 步骤（动作·文件·验证）/ 被否决方案 + 原因 /
风险与回滚 / KILL CRITERIA / 验收标准 / 待验证假设
```

### 执行者建议（必写，不超过 3 行）

议会讨论完，必须回答一句：**这个任务该让谁干**。按任务性质对照：

| 任务性质 | 推荐执行者 | 理由 |
|---|---|---|
| 专业软件脚本（PS JSX / C4D Python / AE 表达式） | 强脚本模型 | 长脚本不易漏 API、少乱改参数 |
| 跨文件重构、架构改动 | 强上下文模型 | 上下文一致性最好，改动边界清楚 |
| 快速小改、查错、跑命令、读日志 | 便宜快速模型 | 成本低、响应快 |
| 看图验收、调色/构图判断 | 多模态模型 | 能稳定读图 |
| 长文档、资料归纳 | 长上下文模型 | 长上下文便宜 |

规则：
- 推荐模型 ≠ 当前执行模型时，**必须明说**：「本任务建议切到 `<模型>` 执行」，并给出 1 句理由。
- **不要拿弱模型硬做专业活**。宁可多花几分钱，也别让免费模型去写 C4D 脚本。
- 执行前问一次用户：切模型 / 还是就用当前的。用户说不用问，就直接按推荐走。

> 具体模型 ID 由用户自己的 provider 决定；本模板不写死任何厂商名。

## 阶段 4 · 执行（带监督）

### 4.1 证据留痕（硬性）

每完成一个「可验证步骤」，写一份证据文件到 `${COUNCIL_DIR:-.council}/runs/<时间戳>/step-N.md`：

```
命令：<原样，含参数>
原始输出：<不删减、不改写、不总结>
改动：<文件清单 + 关键 diff>
验收判据：<怎么算这一步成功>
```

**不许只写“已完成/已修复”。没有原始输出的步骤，一律视为没做。**

### 4.2 独立验收（执行者无权自己判通过）

证据文件写完后，立刻交给 `exec-verifier`：

- 它**自己重跑**验收命令，不看执行者贴的输出
- 它核对「声称」与「证据」是否一致，检查有没有越界改动
- 它输出 `PASS` / `FAIL` / `FAIL(证据不全)`，**执行者不接受申诉**

`FAIL` → 修完重来，最多 3 次；3 次不过走阶段 5。

### 4.3 抽样评审（不全程烧钱）

默认只在 **3 个节点**抽样，其余步骤只做 4.2：

| 节点 | 谁看 | 看什么 |
|---|---|---|
| 第一个能跑通的结果 | `council-architect` | 方向对不对，是不是走歪了 |
| 主要功能完成 | `council-architect` + `council-critic` | 架构与风险，各 ≤300 字 |
| 交付前 | 全部席位（`quick` 模式除外） | 整体验收 |

只有出现**红旗**（验收 PASS 但议员指出设计问题）才升级到全议会重议，不要每步都开会。

### 4.4 其他

- 按定稿推进，todo 记进度。
- 只做方案内改动；有洞走阶段 5。
- 写文件遵守用户项目自己的 `AGENTS.md`；没有就按“先读再改、改完定位”的默认习惯。
- 不把密钥、token、用户隐私写进证据文件。

## 阶段 5 · 降级与失败回流

### 中转站不稳（随时可能 502 / 超时）

- 单席位最多 **2 次**，间隔 3 秒。
- 仍失败 → 用 `general` 子代理 + 显式 `model=` 换备用模型再试 1 次。
- 备用模型按你自己的清单填，例如：

| 席位 | 主 | 备用 1 | 备用 2 |
|---|---|---|---|
| 架构师 | `<architect-primary>` | `<architect-fallback-1>` | `<architect-fallback-2>` |
| 工程师 | `<coder-primary>` | `<coder-fallback-1>` | `<coder-fallback-2>` |
| 反方 | `<critic-primary>` | `<critic-fallback-1>` | `<critic-fallback-2>` |
| 视觉 | `<vision-primary>` | `<vision-fallback-1>` | `<vision-fallback-2>` |
| 学者 | `<scholar-primary>` | `<scholar-fallback-1>` | `<scholar-fallback-2>` |
| 执行 | `<exec-primary>` | `<exec-fallback-1>` | `<exec-fallback-2>` |

- 超时阈值：文本 90 秒。到点就当失败，继续。
- **有效席位 < 3 → 停止议会**，一句话报告谁挂了，不要用 2 个模型硬凑结论。
- 备用模型顶上要标明，不许冒充。

### 执行中卡住（报错 / 假设被推翻 / 同一处 2 次修不好）

打包故障包（步骤 / 期望 / 实际 / **报错原文** / 已试过什么）→ 并行发给 `council-architect` + `council-coder`（架构性问题发全部）→ 各给根因 + 1–2 条修复路径 → 小收敛 → 继续。
**最多 3 轮**，仍不行就停手报告。

## 最终汇报（唯一允许输出的内容，≤500 字）

```
结论：<一句话>

| 席位 | 推荐 | 加权分 | 立场 |
|---|---|---|---|
（N 行）

分歧：<1–2 条，写清谁反对、为什么、最后怎么定的>
改动：<文件 / 步骤，一行一条>
验证：<命令 + 结果摘要>
风险：<还剩什么没解决>
存档：<实际存档路径>
```

`quick` 模式没有互评，表格改成“席位 / 核心主张”两列。
掉线或换模型的席位，在表里标注 `(备用: 模型名)`。
